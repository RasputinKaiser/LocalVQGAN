# Perf Round 3 — iteration-speed plan (NO implementation yet)

Goal: raise it/s at 256² and 512² without changing outputs. Every task is
parity-gated; anything that alters seeded results at 256² is rejected by
policy (bf16@256² precedent: 1.07× was not worth changing seeds).

## Where we are (measured 2026-07-07, M1 16GB, 32cut)

- 256² MLX: 0.85–1.0 it/s. Per-stage (compiled step 1171 ms): synth fwd 336,
  CLIP fwd 189, cutouts 77, loss ~1, backward ≈843. mx.compile is worth 19%.
  Roofline estimate ~1.0–1.3 it/s for this GPU with fp32 VQGAN → we are at
  80–90% of ceiling *given current kernels*. The plan below attacks the
  kernels, not the math.
- 512² MLX (bf16+chunked+4GB cache, fully EAGER, no compile): 0.16–0.25 it/s.
  torch: 0.010/DNF (memory). Biggest headroom is here — the chunked path has
  zero compile/fusion coverage today.
- Rejected already (do not retry without new evidence): fp16 VQGAN (Inf),
  bf16 VQGAN at 256² (seed change), torch.compile/channels_last on MPS,
  whole-step compile of chunked path (per-chunk mx.eval illegal), the
  fixed-shape cutout-matrix reformulation as attempted (0.1% loss divergence
  at iteration 1 — a math bug, see Task 3).

## Benchmark & gate protocol (applies to every task)

- GPU idle (kill preview server + orphans — check `ps aux | grep uvicorn`),
  swap < ~10 GB (`sysctl vm.swapusage`), no taskpolicy, sequential legs,
  5 warmup + 20 timed its at 256², 3 + 10 at 512².
- Gates: seeded final image IDENTICAL at 256² (bit-exact vs current main);
  at 512² identical vs current main's own output (bf16 path is the baseline
  there now). Loss trajectory equality to 1e-5 is the tripwire; the
  discriminating 2-iteration equivalence tests in tests/test_mlx_generator.py
  are the cheap first check. Fast suite green, no new warnings.
- Numbers go to PERFORMANCE.md with commit citation. Ambient-noise caution:
  interleave A/B legs (same conditions) — see the 0.62 vs 0.23 false alarm.
- Codex delegation: Codex sandbox has NO Metal; workers write code in
  /tmp worktrees, verify via host pytest; ALL benchmarks run by orchestrator.

## Tasks, ordered by expected value ÷ risk

### T1. mx.fast fused kernels audit (256² AND 512² — likely the biggest win)
Check whether MlxClip and MlxVQGAN use MLX's fused kernels or hand-rolled
math:
  grep -n "mx.fast" localvqgan/pipeline/backends/mlx_backend/*.py
If absent (suspected), swap in — all exact-math kernel substitutions:
- `mx.fast.scaled_dot_product_attention` in CLIP attention (clip.py
  MultiHeadAttention __call__, line ~83) and the VQGAN mid-block attention
  (vqgan.py). Hand-rolled attention materializes the full QK^T matrix and its
  backward; the fused kernel can be 2–3× on those stages.
- `mx.fast.layer_norm` in CLIP (clip.py line ~111 class, if hand-rolled;
  nn.LayerNorm may already lower to it — verify by profiling, not reading).
- `mx.fast.rms_norm` n/a. GroupNorm: check whether `nn.GroupNorm
  (pytorch_compatible=True)` and our Fp32GroupNorm lower to a fused kernel;
  if Fp32GroupNorm's manual upcast blocks fusion, measure a
  `mx.fast.layer_norm`-style rewrite ONLY if bit-parity holds.
Gate: embedding cosine >0.999999 vs current, seeded 256² image bit-exact.
Est: CLIP fwd 189→~120 ms and a chunk of the 843 ms backward; plausibly
+10–20% at 256², more at 512² (32 cutouts of attention per chunk).

### T2. Backward attribution profile (prerequisite for T4/T5)
The 843 ms backward at 256² is unattributed. Split with two-stage vjp:
time (a) d(loss)/d(out) (CLIP+cutouts backward), (b) synth pullback (decoder
backward). Also per-layer decoder timing via eval barriers. Deliverable: a
table in PERFORMANCE.md; decides whether decoder-bwd or CLIP-bwd dominates.
No gate needed (measurement only). Script skeleton exists:
scratchpad mlx_256_profile.py from 2026-07-07 session (rewrite fresh, it's
in /private/tmp and may be gone).

### T3. Chunked-path compile reuse, root-caused this time (512²)
The previous attempt failed with ~0.1% loss divergence at iteration 1 —
that magnitude at iteration 1 means a real math bug in the reformulated
crop+resize weight matrices, NOT float reassociation or an inherent blocker.
Approach: bisect the old attempt (its diff is in git history of the
codex/chunked-cutouts branch, commits 569cb35..4c56ec3 range — the reverted
mechanism `make_cutout_weight_matrices`/`apply_weighted_cutout_batch`) 
against eager per-op: cutout crop, resize, sharpness border, normalization.
Find the diverging op, fix, re-run the discriminating equivalence test
(exact match expected, as eager chunking achieved loss diff 0.0).
Then: ONE compiled per-chunk fn taking (out, spec-slice arrays) as args,
compiled once per generation, remainder chunk eager.
Gate: equivalence test with compile ON, exact; then benchmark.
Est: up to ~19% at 512² (the measured compile margin at 256²).

### T4. Compile the synth fwd + pullback separately (512²)
Independent of T3: the decode fwd and its vjp are fixed-shape per generation
and contain no per-chunk eval — they can be mx.compile'd even while the
chunk loop stays eager. Decode is ~40% of iteration at 512².
Gate: bit-exact 512² output vs eager. Est: 5–15% at 512².

### T5. Cutout-chunk size sweep (512², trivial)
CUTOUT_CHUNK_SIZE 8 → try 16 and 32-with-cache-limit at 512²: fewer
eval barriers, more parallelism, still bounded. Also sweep cache limit
2/4/6 GB. Pure measurement, no gate beyond stability (no swap growth over
20 its). Est: 0–10%.

### T6. mx.async_eval chunk pipelining (512², only after T3/T5)
Overlap chunk N+1 graph construction/launch with chunk N compute:
`mx.async_eval(chunk_loss, chunk_grad)` then synchronize before the
accumulate. Cap in-flight at 2 or peak memory doubles (defeats chunking).
Gate: identical outputs + no swap growth. Est: 5–10% at 512². Skip if T3
lands compile (less Python overhead to hide).

### T7. Fold cutout crop+resize into one batched GEMM (256², small)
The matmul-form resize already exists; crop is a slice. Composing them into
per-cutout one-hot row/col matrices makes all 32 cutouts ONE batched matmul
pair. Cutouts are 77 ms (6.6%) at 256² — cap the effort accordingly, and
note T3's divergence bug lives in exactly this kind of reformulation:
reuse whatever T3 root-causes. Gate: bit-exact. Est: 2–4% at 256².

### T8. Adam step + z-clamp inside the compiled graph (256²)
Today: compiled value_and_grad, then eager opt.apply_gradients + mx.clip +
eval. Folding the optimizer update into the compiled fn (optimizer state as
explicit args/returns) removes per-iteration graph-build overhead and two
kernel launches. mlx.optimizers supports functional-style updates.
Gate: 3-step trajectory test vs torch (exists: test_adam_matches_torch_
bias_correction) + bit-exact seeded image. Est: 3–8% at 256².

### T9. torch decoder gradient checkpointing (torch engine, 512², CUDA users)
torch.utils.checkpoint on the VQGAN decoder up-blocks: recompute activations
in backward, same math, deterministic. Purpose: stop 512² swap-death for
torch-only users (Windows/Linux/low-VRAM CUDA); on this M1 it may make torch
512² merely slow instead of DNF. Gate: bit-exact torch output (checkpointing
is exact; verify RNG handling with preserve_rng_state=True for the aug RNG).
Est: torch 512² 0.01→~0.15–0.25 it/s on 16 GB (from the 0.284 compute
profile minus recompute overhead).

### T10. Preview/eval hygiene sweep (both engines, small)
- Preview decode at display_freq reuses the loop's `preview_z` but runs a
  SECOND full _synth at 256²+ (generator.py line ~227/308). Cache the decode
  from the loss graph? Not accessible under compile — instead decode at
  bf16 for preview only at large canvas (preview is JPEG'd anyway; NOT the
  saved final frame — final must stay exact). Gate: final PNG bit-exact;
  previews are display-only. Est: smooths preview stutter, ~2% avg.
- Check `_loss_is_finite` (np.array(mx.isfinite(loss))) doesn't force an
  extra sync per iteration — fold into the existing eval.

### Explicitly out of scope (would change outputs or product)
- Reducing iterations/cutouts/step-size; low-res optimize + upscale;
  quantized CLIP; fp16 VQGAN anywhere; bf16 VQGAN at ≤256²; changing augs.
